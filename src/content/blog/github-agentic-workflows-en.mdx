## Understand it in 30 seconds
Ordinary GitHub Actions suits deterministic steps: build, test, lint, and deploy.
`gh-aw` addresses another kind of task: reading issues, inspecting code, interpreting context, and deciding what to do next.
You write a Markdown workflow. Its frontmatter defines triggers, permissions, tools, and the model; its body describes the task. `gh aw compile` turns it into a standard Actions workflow. The agent is read-only by default and runs in a sandbox. Writing back to the repository goes through controlled outputs.
The important part is that the agent's freedom stays within the existing CI permission model.
## Why it is interesting
Most agent automation demos start with what the agent can do. `gh-aw` first addresses what gives it permission to do it.
That is closer to production requirements. CI already has triggers, permissions, secrets, logs, auditing, and failure records. Rather than rebuild an agent platform, `gh-aw` connects reasoning steps to that infrastructure.
## 3 designs worth borrowing
### 1. Separate intent files from execution files
People maintain `.md`; machines execute the compiled `.lock.yml`. Natural language is easy to edit, while the executable result remains an inspectable Actions file.
### 2. Withhold write access by default
The agent first reads, analyzes, and produces results. Actual changes to issues, PRs, or repository content go through explicit safe outputs. Permissions are execution-layer constraints, rather than reminders in a prompt.
### 3. Keep deterministic CI
Tests, builds, and deployments continue to use ordinary Actions. Only the parts that require judgment go to the agent. This is easier to debug and cheaper than turning every step into an agent task.
## How this connects to my work
The most useful idea to borrow is **separating the agent harness from the business workflow**.
When building agent runtimes, tool calls, permissions, and automation, you can apply these principles directly:
- Keep deterministic tasks in ordinary programs.
- Enter the agent loop only when interpretation or judgment is needed.
- Put agent permissions at the runtime or tool boundary, rather than only in the system prompt.
- Prefer compiling natural-language configuration into auditable execution artifacts.
This structure also suits multi-agent systems: define goals at the top, generate constrained execution plans below, and let the tool layer carry them out.

## Sources and fact checks
- Project: GitHub Agentic Workflows; CLI name: `gh-aw`.
- Maintainer: GitHub Next / GitHub.
- Core function: define agent workflows with Markdown and YAML frontmatter, then use `gh aw compile` to generate standard GitHub Actions `.lock.yml` files.
- Suitable tasks: issue triage, PR review, CI failure investigation, documentation maintenance, dependency analysis, repository reports, and other tasks that require judgment or explanation.
- AI engines: GitHub Copilot, Claude Code, OpenAI Codex, Google Gemini, and Pi.
- Security defaults: the agent job is read-only by default and runs in a sandbox; write operations generally go through constrained safe outputs.
- LICENSE: MIT.
