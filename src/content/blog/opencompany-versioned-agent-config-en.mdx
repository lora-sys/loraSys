The original cover retains its Chinese labels. They mean "version history," "narrow permissions," and "human sign-off." The company.toml file records the configuration, each layer reduces available permissions, and a person approves designated actions.

## Fact check
- Project name: OpenCompany.
- Organization: Tiny Humans, with the GitHub organization `tinyhumansai`.
- Official positioning: an agent-team runtime layer for one-person businesses.
- Core structure: each company lives under `companies/`. Its `company.toml` defines company information, agent organization, tool permissions, groups, connections, workflows, and policies.
- Human control: company configuration can specify `human_role`. The official Marketing Agency example sets it to `Campaign review and sign-off`.
- Tool permissions: the Marketing Agency example narrows tool permissions across company, desk, and agent levels. Configuration comments explicitly state that these permission sets are intersected across the hierarchy.
- Demo: the official README provides `launch-demo.sh`. Once it starts, the local Operator Console lets users watch agents work and handle items awaiting human approval.
- Models and execution: real agent work requires a TinyHumans API key to use Medulla. Without a key, users can still start and inspect the interface, but agents do not perform real work.

- Current status: source code and a local demo are available. The official README explicitly labels the project WIP and `Not production-ready`. The official website still has a waitlist.
- LICENSE: GPL-3.0.

## The 30-second version
OpenCompany treats a company as a runnable configuration package.
Each company is a directory. Its `company.toml` specifies the company name, human responsibilities, agent team, tool permissions, groups, connections, workflows, and policies. The host reads this configuration and instantiates the agents. People approve or decide matters at the points designated in the configuration.
It released v0.1.4 today. The source code and local demo can run, but the project is still officially marked WIP, with an explicit warning against relying on it as a production system.
## Main assessment
The part most worth borrowing is the conversion of organizational design into configuration files, rather than the "one-person company" slogan.
If roles, permissions, and human approvals exist only in prompts, the system is difficult to audit or compare between revisions. Once those rules are in `company.toml`, they can be committed to Git, reviewed as diffs, and checked before deployment.
## Why it is interesting
Many multi-agent demos start by drawing an organization chart and letting different agents message each other. OpenCompany goes a step further by mapping that chart to executable configuration.
The Marketing Agency manifest directly records the human sign-off responsibility, each agent's desk, permitted tools, intended Slack or Gmail connections, enabled workflows, and approval policies. It puts "who can do what" into a concrete repository file.
The project remains WIP, so it should not be used as proof that the one-person company is already a mature model. It is more useful as an example of agent-product architecture.
## 3 designs worth borrowing
## 1. The company is configuration
`company.toml` is the stable entry point. Organizational structure lives in a version-controlled file as well as the UI. Changes to roles, permissions, and workflows all produce diffs.
## 2. Narrow permissions at each level
The Marketing Agency example separates company-wide, desk-level, and agent-level tool sets. Lower levels can only narrow access further, not expand it on their own. This approach suits any multi-agent system with high-risk tool calls.
## 3. Put human sign-off into the structure
`human_role` and approval policies appear directly in the configuration. When people intervene does not depend on an agent's improvised judgment. For publishing, payments, contracts, and high-cost actions, this design is more controllable than a line saying "ask the user when necessary."
## How this connects to my work
Your current content workflow could be rewritten using the same structure.
Research, fact-checking, writing, visuals, and review can be separate agents. Database fields, source requirements, and scoring rules can go into a manifest. Final publication stays with a person. The daily process then no longer needs an ever-longer prompt to remain consistent.
If you later build a multi-agent product, you can also put AgentCard definitions, tool permissions, and human intervention points into the same project-level configuration for the runtime to read.
