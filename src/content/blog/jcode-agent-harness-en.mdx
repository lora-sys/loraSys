## The 30-second version
Many coding-agent multitasking setups amount to running several processes. As the number of agents grows, RAM, context, conflicts, and state synchronization quickly become problems.
`jcode` starts with the harness. It implements a terminal agent in Rust and connects multiple sessions to the same server. If Agent A changes a file that Agent B has already read, the server notifies B. Agents can also send private messages and broadcasts, and the main agent can launch workers itself.
It also puts unfinished todos, changes in confidence, context caching, and continued execution into the harness instead of relying on the model to remember everything.
The useful question with projects like this is how agents keep working, beyond the chat interface.
## Why it is interesting
Differences between coding agents are increasingly hard to explain through model names alone. With the same model, different tools, context, caching, verification, and continuation strategies can produce substantially different results.
`jcode` makes this concrete. It even states publicly that `the harness matters as much as the model`.
I am more interested in how it handles multi-agent state. Parallel work is more than starting four models at once. The hard part is deciding who knows a file has changed, who handles conflicts, and who determines whether the task is actually complete when four agents edit the same repository.
## 3 designs worth borrowing
### 1. Share server state across agents
The agents are more than independent terminals. The server knows which agents are working in the same repository and can notify them when code changes affect their context.
That is closer to a collaborative runtime than worktree-based parallel execution alone.
### 2. Put the verification loop in the harness
jcode todos record task assignment and confidence at completion. The project also has an automatic continuation mechanism. If a turn ends while todos remain unfinished, the harness can prompt the model to keep working.
This is useful for agent evals. Measure task states, verification actions, failure points, and the number of continuations, as well as the final answer.
### 3. Treat resource efficiency as multi-agent infrastructure
The most direct costs of multiple agents are processes, memory, caches, and provider requests. jcode measures the PSS of additional sessions and uses a server/client architecture to reduce duplicated overhead.
If you want to run 10 or 20 agents, these metrics are more useful than the number of nodes drawn in the UI.
## How it connects to my work
This project is close to your current interests in agent harnesses, evals, and multi-agent runtimes.
Four pieces are worth studying directly:
- `server/client`: what state agents share and what state must remain isolated.
- `swarm`: how agents find teammates, exchange messages, and know whether another agent has finished.
- `todo + confidence`: how to turn execution into measurable events rather than looking only at final answers.
- `auto-poke`: how long-running tasks decide to continue instead of stopping as soon as the model says "done."
If you are building your own agent eval framework, I would borrow the event model and verification points before the UI.
