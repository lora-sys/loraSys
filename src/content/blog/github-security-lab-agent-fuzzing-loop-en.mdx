### Core mechanism
The project targets native C and C++ repositories. It analyzes the target code and build process, generates fuzz harnesses, runs AFL++, reads coverage, and adjusts the next iteration based on uncovered branches.
The official design separates responsibilities. The LLM agent decides what target to fuzz, how to modify the harness, and which coverage gap to pursue next. Tools compile and run code, read coverage, and save results.
Workflow state is stored in SQLite. Existing state and the corpus remain usable after a campaign stops.
Each harness has a fuzzing build and a coverage build. The former performs the tests; the latter generates more readable source-code coverage. Based on uncovered paths, the agent decides whether to add seeds, modify the harness, expand the dictionary, or skip low-value paths.
### Demo and current availability
The most direct way to try it is to follow the official repository instructions and run a target repository in a disposable development environment. Once a campaign starts, it provides an HTML dashboard. The official article shows coverage trends, a crash heatmap, and an iteration timeline.

### Safety note
The official documentation explicitly warns that this workflow runs compilation and testing tools on the host, without container isolation. It recommends a disposable Codespace or temporary virtual machine with restricted permissions.

## Understand it in 30 seconds
The difficult part of ordinary fuzzing is not starting the run. It is continually reviewing coverage, extending harnesses, pursuing unvisited branches, and organizing results afterward.
This project gives the repeated judgment calls to an agent. AFL++ still runs the tests, while clang and lcov still measure coverage. The agent reads each round of results and decides what to change next.
What makes it worth examining is a measurable feedback loop: execute, measure, judge, and execute again.

## Why it is interesting
Many agent projects make the model handle every action. This project narrows the model's role.
The model does not simulate AFL++ or calculate coverage itself. It handles only the parts that require judgment. Execution results then become inputs to the next iteration.
The effect of an agent's changes can therefore be assessed directly through coverage changes, without relying on the model's own statement that the task is complete.

## 3 designs worth borrowing
First, separate decisions from execution. The model chooses the next step, and programs perform verifiable actions.
Second, feed measurable signals directly into the next iteration. External metrics can show whether each change had an effect.
Third, persist state. Store historical results in structured storage instead of relying on a long conversation to retain context.
